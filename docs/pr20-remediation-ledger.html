7.5

Update device status in near real time

Was partial
Audit required

Implement stale and offline transitions. A silent device could stay visually Online; staleness was computed only when queried, the page never refetched device state, and device_state used the global threshold rather than the session's own stale_after_seconds. A retained link-offline heartbeat could read as Online.

What was done

Three backend-authored states replace the single boolean: online, stale, offline. The threshold is now resolved from live_sessions, so two sessions that declared different thresholds transition at different times.

A reported link loss is checked first and renders Offline regardless of timestamp recency — the exact misreading the audit named. With nothing being reported, the SSE heartbeat drives a device refetch, so the transition stays a backend decision the browser only displays. The legacy stale flag is retained and true for both non-online states.

7.9

Add safe reconnect behaviour

Was partial
Audit required

Add gap recovery and cursor continuity. A cursor older than the earliest retained message resumed silently, so the feed could omit data with no signal. Pause also rebuilt the data source — paused was an effect dependency — resetting its cursor and replaying retained history.

What was done

A versioned stream.reset frame is emitted before any later message when Last-Event-ID predates the retained window, carrying reason: cursor_expired, the oldest retained id, a resume cursor and the list of resources to refetch. The browser discards its display buffers and rebuilds devices, metrics, timeline, events and alerts from the authoritative APIs.

The check reads the global low-water mark, since stream_id is one sequence pruned globally. It is deliberately conservative: pruning that removed only other cases' messages still reports a gap. One unnecessary refetch is the right trade against ever missing a real one.

paused moved into a ref, so one stream is held for the life of a case and session. Pausing the display no longer tears down the connection or resets the cursor — so no replay, and no eventual duplicates once the bounded seen-id cache rolls over.

11.2

Generate alert email drafts

Was partial
Audit required

Generate grounded draft content and connect the frontend. The endpoint stored caller-written text against an alert hash without generating anything from the alert, phase3Api exposed no method, and no connected page called it — so the feature was inaccessible and could produce a draft unrelated to its anchor.

What was done

Only a recipient is required now. The backend composes the subject and body from the persisted alert — id, rule, title, severity, risk score, trigger time, finding and a bounded evidence list — with no model involved. A notification-preview endpoint returns that same text before any record is written.

Cross-case and unknown identifiers are refused with 404, since an artifact is resolved inside its own case's latest analysis run. A shared notification panel in the alert drawer carries create, edit, approve and send; Live Monitor's alert cards deep-link straight into it.

11.10

Preserve alert and notification audit history

Was partial
Audit required

Complete lifecycle auditing and workflow-status synchronisation. Creation, approval and completed SMTP outcomes were recorded, but draft edits and rejected sends were not, and a sent alert notification never updated alert_workflow.notification_status — so the alert list could keep reporting not_requested after delivery.

What was done

email_draft.updated records which fields changed, both content hashes and whether an approval was revoked — the field names, never the new values, so an edit is reconstructible without republishing the message.

email.rejected records a refused send or approval with a bounded code from a closed vocabulary (approved_email_required, email_content_changed, smtp_not_configured, recipient_domain_not_allowed, artifact_not_found and three more) plus the request id. A raw exception string can never reach the audit details.

A terminal outcome is mirrored onto the alert — delivered or delivery_failed — in the same transaction as the delivery attempt and the draft's terminal state, so the two views cannot disagree. Incident notifications deliberately leave individual alert rows alone rather than overstating what was sent.

Required hardening before merge

Not a roadmap checkmark
H.1

Legacy email draft migration test

Added
Audit required

The table rebuild in SQLiteRepository was uncovered. It changes report_id from required to nullable and must preserve existing approvals and delivery records. The audit asked for an explicit transaction, foreign-key restoration in a finally path, PRAGMA foreign_key_check, idempotency across two initialize() calls, and proof that no temporary table survives success or failure.

What was done

The copy, drop and rename now run inside one explicit transaction. executescript was removed deliberately — it commits any open transaction before running, which would have defeated exactly the atomicity being asked for. PRAGMA foreign_key_check runs before the commit and enforcement is restored in a finally path.

Legacy rows additionally recover their case_id from the report they belong to, so an old draft still appears in its case's list instead of vanishing from the UI.

The backend suite now runs in roughly 430 seconds locally, because these tests drive real authenticated telemetry through the worker rather than seeding fixtures.
